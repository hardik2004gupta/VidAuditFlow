# API_PLAN.md
## VidAuditFlow — Target REST API Design

Style: REST, resource-oriented, versioned under `/api/v1`, JSON in/out, JWT bearer auth on every route except `/health`. Full architectural rationale (async, error handling, background tasks) lives in `BACKEND_VISION.md`; this document is the endpoint-by-endpoint contract.

---

## Versioning Strategy

- All business routes are prefixed `/api/v1/...`. There is no unversioned API surface.
- A breaking change to a response shape ships as `/api/v2/...` running alongside `/api/v1/...` until the frontend (which lives in the same repo and deploys in lockstep) migrates — practically, for a single-consumer portfolio project, this mostly future-proofs the *pattern* rather than solving a real multi-consumer versioning problem today. No breaking v2 is planned as part of this modernization; the prefix is added now because retrofitting versioning onto an unversioned API later is the more expensive path.
- OpenAPI schema (auto-generated by FastAPI) is the single contract source; the frontend's `lib/types.ts` is kept in sync with it (manually or via `openapi-typescript`, see `FOLDER_STRUCTURE_V2.md`).

---

## Authentication

- **Mechanism:** Supabase Auth issues a JWT on login/signup (frontend talks to Supabase directly for this — the backend never handles raw passwords).
- **Every `/api/v1/*` route (except `/health`)** requires `Authorization: Bearer <supabase_jwt>`.
- **Verification:** `core/security.py` validates the JWT signature against Supabase's published JWKS and checks expiry; on success, extracts `sub` (Supabase user id) and resolves/creates the corresponding local `users` row (see `DATABASE_PLAN.md`).
- **Failure responses:** missing/invalid/expired token → `401 Unauthorized` with `{"error": {"code": "unauthorized", "message": "..."}}`. A valid token for a resource the user doesn't own → `404 Not Found` (not `403`) for job/report lookups, deliberately avoiding confirming a resource's existence to a non-owner.

## Endpoints

### `GET /health`
- **Auth:** none.
- **Purpose:** liveness/readiness check for Render/Railway and uptime monitoring.
- **Response `200`:**
```json
{ "status": "healthy", "service": "vidauditflow-api", "version": "2.0.0" }
```

---

### `POST /api/v1/audits`
- **Auth:** required.
- **Purpose:** kick off a new compliance audit. Returns immediately; the actual pipeline runs in the background (see `BACKEND_VISION.md` → Background Tasks).
- **Request model (`AuditCreateRequest`):**
```json
{ "video_url": "https://youtu.be/dT7S75eYhcQ" }
```
  - `video_url: str` — validated via a Pydantic validator: must parse as a URL with host in `{youtube.com, www.youtube.com, youtu.be}` (closes the audited soft-SSRF substring-check finding).
- **Response `202 Accepted` (`AuditJobRead`):**
```json
{
  "id": "b3f1...":
  "status": "queued",
  "current_stage": null,
  "video_url": "https://youtu.be/dT7S75eYhcQ",
  "video_id": "vid_b3f1a9c2",
  "created_at": "2026-07-01T10:00:00Z"
}
```
- **Status codes:** `202` created and scheduled; `400` invalid URL (fails Pydantic validation before hitting business logic); `401` unauthenticated; `429` per-user daily quota or concurrent-job cap exceeded (see `BACKEND_VISION.md`).
- **Idempotency note:** if the same user already has a `queued`/`running` job for the same `video_url`, the existing job is returned with `200 OK` instead of creating a duplicate.

---

### `GET /api/v1/audits`
- **Auth:** required.
- **Purpose:** list the current user's audit history (for the dashboard).
- **Query params:** `limit` (default 20, max 100), `offset` (default 0), `status` (optional filter: `queued|running|completed|failed`).
- **Response `200` (`List[AuditJobRead]`):** array of the same shape as the create response, newest first.

---

### `GET /api/v1/audits/{job_id}`
- **Auth:** required (must own the job).
- **Purpose:** poll a single job's status — the primary endpoint the live-tracker UI calls repeatedly (or subscribes to via SSE, see below).
- **Response `200` (`AuditJobRead`):**
```json
{
  "id": "b3f1...",
  "status": "running",
  "current_stage": "compliance_analysis",
  "video_url": "https://youtu.be/dT7S75eYhcQ",
  "video_id": "vid_b3f1a9c2",
  "error_message": null,
  "created_at": "2026-07-01T10:00:00Z",
  "updated_at": "2026-07-01T10:02:14Z",
  "completed_at": null,
  "report_id": null
}
```
  - Once `status == "completed"`, `report_id` is populated so the client knows to fetch `GET /api/v1/reports/{report_id}`.
- **Status codes:** `200`; `404` if the job doesn't exist or isn't owned by the caller.

---

### `GET /api/v1/audits/{job_id}/stream` *(optional SSE variant of the above)*
- **Auth:** required.
- **Purpose:** Server-Sent Events stream of job status updates, as a nicer alternative to client-side polling for the live tracker — kept genuinely optional (polling every 2–3s is a perfectly acceptable fallback and simpler to implement first; SSE is a `Should Have` enhancement, not required for MVP).
- **Response:** `text/event-stream`, one `AuditJobRead`-shaped event per stage transition, closed automatically when the job reaches a terminal state.

---

### `GET /api/v1/reports/{report_id}`
- **Auth:** required (must own the parent job).
- **Purpose:** fetch the finished report for the interactive report page.
- **Response `200` (`ReportRead`):**
```json
{
  "id": "d8a2...",
  "audit_job_id": "b3f1...",
  "final_status": "FAIL",
  "final_report": "This video contains 2 critical violations related to...",
  "compliance_results": [
    {
      "category": "Misleading Claims",
      "severity": "CRITICAL",
      "description": "Absolute guarantee of results detected at 00:32.",
      "source_citation": "FTC Influencer Guide, Section 3.2",
      "timestamp": "00:32"
    }
  ],
  "video_metadata": { "duration": 245, "platform": "youtube" },
  "pdf_export_url": null,
  "created_at": "2026-07-01T10:04:41Z"
}
```
- **Status codes:** `200`; `404` not found/not owned.

---

### `POST /api/v1/reports/{report_id}/export`
- **Auth:** required.
- **Purpose:** generate (or return a cached) PDF export of the report, uploaded to Supabase Storage.
- **Response `200`:**
```json
{ "pdf_url": "https://<supabase-project>.supabase.co/storage/v1/object/public/reports/d8a2....pdf" }
```
- **Status codes:** `200` (including on cache-hit, same response shape); `404` report not found; `500` PDF generation failure (mapped through the standard error envelope, no raw exception text — see `BACKEND_VISION.md`).

---

### `POST /api/v1/reports/{report_id}/chat`
- **Auth:** required.
- **Purpose:** ask a follow-up question about a specific completed report, grounded in that report's retrieved policy chunks (reuses the Retrieval Agent's pattern — see `AI_PIPELINE_VISION.md`).
- **Request model (`ChatMessageRequest`):**
```json
{ "message": "Why was the guarantee claim flagged as critical?" }
```
- **Response `200` (`ChatMessageResponse`):**
```json
{
  "reply": "The claim at 00:32 promises guaranteed results, which the FTC Influencer Guide (Section 3.2) explicitly prohibits without qualifying language...",
  "citations": ["FTC Influencer Guide, Section 3.2"]
}
```
- **Status codes:** `200`; `404` report not found/not owned; `422` empty/invalid message.
- **Note:** chat history for a report is not persisted as its own table in the MVP (kept in the frontend's client-side state per session) — see `FEATURE_ROADMAP.md`/`DATABASE_PLAN.md` for why a `chat_messages` table is a reasonable Future addition, not a day-one requirement.

## Response Envelope & Status Code Conventions

| Situation | Status | Body shape |
|---|---|---|
| Success (single resource) | `200` | The resource itself (no wrapper envelope) |
| Success (resource created, work scheduled) | `202` | The created resource (job), reflecting its initial `queued` state |
| Validation error (bad input) | `422` | FastAPI's default Pydantic validation error shape |
| Domain validation error (e.g., disallowed URL host) | `400` | `{"error": {"code": "invalid_url", "message": "..."}}` |
| Unauthenticated | `401` | `{"error": {"code": "unauthorized", "message": "..."}}` |
| Not found / not owned | `404` | `{"error": {"code": "not_found", "message": "..."}}` |
| Rate limit / quota exceeded | `429` | `{"error": {"code": "quota_exceeded", "message": "..."}}` |
| Upstream (Azure) failure after retries exhausted | `502` | `{"error": {"code": "upstream_error", "message": "..."}}` |
| Unexpected server error | `500` | `{"error": {"code": "internal_error", "message": "Something went wrong. Reference: <request_id>"}}` |

No endpoint ever returns a raw Python exception string in a response body — closing the audit's Medium-severity "verbose internal error messages returned to API clients" finding across the entire API, not just the one route it was originally found on.

## CORS

- `CORS_ALLOWED_ORIGINS` (from `core/config.py`) lists the exact Vercel production domain and `localhost:3000` for local dev — no wildcard `*` origin, ever, since the API is authenticated and cookie-free (bearer token only), but a precise allow-list is still the correct default over a wildcard.

## Rate Limiting

- A lightweight per-user limiter (in-memory token bucket, or a `requests_this_minute` check against `audit_jobs`/a small counter table) applied to `POST /api/v1/audits` and `POST /api/v1/reports/{id}/chat` specifically — the two routes that trigger billable Azure calls. Read-only routes (`GET /audits`, `GET /reports/{id}`) are not rate-limited beyond normal infra-level protection.
